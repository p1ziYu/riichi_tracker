# 外部技术评审核对与修订记录

日期：2026-10-19。评审材料为用户提供的 8 页 PDF；它提出的是待核对意见，不自动成为产品需求。已确认的线下实体麻将、三端、全员录入、实时同步、账户安全和开局二维码签到保持不变。本记录只说明设计取舍；尚无应用代码、数据库 migration 或真机实测。

| 评审点 | 核对结论与修订 | 落点 |
|---|---|---|
| 局中立直与结算竞态 | 成立。改为持久化共享标记，局末确认成立集合；同一结算事件扣立直棒、结算和牌及分配供托。结算使用本局结果版本和已确认标记版本；过时标记触发新预览，保留输入。 | [计划书 §4.4、§7.2](日麻三端产品计划书.md)，[数据库 §6–8](数据库设计.md) |
| 全桌断网与开局签到 | 成立。全桌离线仅能做单设备草稿，不能写成已完成云端到场签到；转正式战绩需联网重新开桌、现场确认和逐局核对。 | [计划书 §7.3、§8.1](日麻三端产品计划书.md) |
| 二维码频繁换代破坏入桌幂等 | 成立。固定邀请活动行，二维码由时间窗与服务端 HMAC 产生；只有重置／开局改 generation。每桌每身份至多一条待处理申请。 | [数据库 §5、§7](数据库设计.md) |
| Better Auth 内部会话行锁 | 成立。业务事务不直接操作认证组件内部表；通过其会话接口先验证，业务事务复核自身身份和成员状态。撤销与在途请求的竞态明确标出，不承诺跨组件绝对即时原子性。[官方会话文档](https://better-auth.com/docs/concepts/session-management)。 | [计划书 §6.1](日麻三端产品计划书.md)，[数据库 §3、§8](数据库设计.md) |
| 访客设备丢失 | 成立。加入凭证关闭后，原席位由房主／共同主持现场核对，签发单次恢复凭证并撤销旧访客会话；重扫失效二维码不得冒领。 | [计划书 §8.2](日麻三端产品计划书.md)，[数据库 §3.2](数据库设计.md) |
| 终局剩余供托 | 成立。先用不含场上剩余供托的实际持点判断是否终局；确定结束后按固定同点座次选暂定首位，从供托账户实际转点，再计算最终顺位和竞技分。 | [计划书 §4.5](日麻三端产品计划书.md)，[数据库 §9](数据库设计.md) |
| 诈和与竞技术罚分 | 部分成立。首发只支持本局作废／重打或有理由的人工裁定；自动诈和支付与局末竞技分罚符列 P1，不把不同赛事规则混为一套。预留处罚字段，P0 为零。 | [计划书 §4.4、§3.2](日麻三端产品计划书.md)，[数据库 §6、§9](数据库设计.md) |
| 三麻本场、流局罚符 | 成立。拟定三麻家规改为荣和每本 200、自摸每位付款者每本 100；3,000 点荒牌流局按一听／两听列明每人 1,500 点。规则是产品家规模板，不宣称全平台通用。 | [计划书 §4.2、§12.1](日麻三端产品计划书.md) |
| 低点立直与西入边界 | 成立。少于 1,000 点不能确认成立立直，0 点是否结束、负分何时判定与剩余供托是否计入目标点已写清，均在完整结算后判断。 | [计划书 §4.4–4.5](日麻三端产品计划书.md) |
| 多人正在录入、房主离线 | 成立。录入提示是可过期软状态，不锁牌局；共同主持可处理规定的成员管理，所有参赛者继续记分。 | [计划书 §7.1、§8.1](日麻三端产品计划书.md) |
| 较早局自动重算后续真实局 | 成立。P0 只修订无后续依赖的最近局；更早结果先标争议，保留实际打过的后来局。P1 的历史修订必须区分规则模拟和经玩家核对的事实重录。 | [数据库 §9](数据库设计.md) |
| 移动端 WebSocket 鉴权 | 成立。浏览器原生构造器没有任意认证头参数；三端先经 HTTPS 领取短期一次性票据，WSS 打开后首帧验票，验票前不推送私密内容。[WebSocket API](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket/WebSocket)。 | [计划书 §6.1](日麻三端产品计划书.md)，[数据库 §8](数据库设计.md) |
| 密码哈希与服务器容量 | 成立为风险，不是当前已发生的性能故障。阶段 A 核验默认 scrypt 参数或显式 Argon2id，限制并发并测目标服务器；2 vCPU／4 GB 不作为 50 桌容量保证。[OWASP 参数](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)。 | [计划书 §6.1、§9.2、§12.4](日麻三端产品计划书.md) |
| iOS 原生壳与排期 | 审核风险成立，实际是否通过由 Apple 决定。加入原生扫码、深链、安全存储和断线恢复真机门槛；双人首发估算调整为 21 周加 3 周缓冲。[Apple 4.2](https://developer.apple.com/app-store/review/guidelines/)。 | [计划书 §9.4、§11](日麻三端产品计划书.md) |
| 减少首发账户功能 | 部分采纳。普通用户 TOTP、完整管理员后台与复杂赛事罚分放到 P1；邮箱验证、密码找回、设备撤销和自助账户删除保留 P0，满足用户提出的账户安全目标及上架前账户删除准备。[Apple 删除要求](https://developer.apple.com/support/offering-account-deletion-in-your-app/)。 | [计划书 §5、§11](日麻三端产品计划书.md) |
| 数据库结构与索引 | 成立。补全座位结果、复合责任字段预留、签到失效、待处理申请唯一性、剩余供托、处罚字段、按事件 ID 的账本索引及同桌复合外键。访客升级采用身份别名，不批量改历史作者 ID。 | [数据库 §3–9](数据库设计.md) |
| 统计按完整规则哈希碎片化 | 成立。基础汇总按人数、东风／半庄及顺位结算配置分组，精确规则版本从原始结算事实筛选，避免每个微小家规产生单独汇总行。 | [数据库 §9](数据库设计.md) |

仍须在开发阶段验证：三端原生安全存储与一次性 WebSocket 票据、认证撤销时序、密码哈希吞吐、规则样本、数据库约束与备份恢复。上述均是设计与验收要求，不是已经通过的测试结果。
